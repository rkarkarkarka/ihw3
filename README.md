## Запуск и тестирование

### Проверка установки
Перед запуском проекта убедитесь, что установлены:
```bash
docker --version
docker-compose --version
```

### Запуск проекта
Перейдите в корневую директорию проекта и выполните:
```bash
docker-compose up --build
```

### Доступные интерфейсы:
- **API Gateway Swagger**: http://localhost:8080/swagger  
- **Orders Service**: http://localhost:5001/swagger  
- **Payments Service**: http://localhost:5002/swagger

### Остановка:
```bash
docker compose down --volumes
```


## Архитектура проекта

### Компоненты
- **API Gateway (8080)** — единая точка входа для всех запросов, маршрутизирующая их между сервисами  
- **Orders Service (5001)** — управление заказами и их статусами  
- **Payments Service (5002)** — обработка платежей и управление счетами  
- **PostgreSQL (2 БД)** — отдельные хранилища данных для каждого сервиса  
- **RabbitMQ (5672, 15672)** — асинхронный обмен событиями между микросервисами

### Архитектурные особенности
- Разделение данных по принципу *Database per Service*  
- Асинхронное взаимодействие с помощью *Transactional Outbox Pattern*  
- Полная контейнеризация через Docker и управление через Docker Compose  


## Функциональность сервисов

### API Gateway
- Использование YARP (Reverse Proxy) для проксирования и маршрутизации  
- Агрегация документации Swagger  
- Поддержка CORS для корректной работы с фронтендом  
- Преобразование путей и маршрутизация запросов к нужным микросервисам  

### Orders Service
- Создание заказов с автоматическим запуском оплаты через RabbitMQ  
- Получение списка заказов по `userId`  
- Автообновление статуса заказов в зависимости от результата оплаты  
- Использование Outbox-таблицы для надёжной генерации событий  

### Payments Service
- Регистрация счета пользователя (один счет на пользователя)  
- Пополнение баланса с атомарной обработкой операций  
- Отображение текущего баланса  
- Обработка платежей с гарантией "exactly once", предотвращающей дублирование списаний  


## Основные сценарии взаимодействия

### 1. Создание и автоматическая оплата заказа
Клиент → API Gateway → Orders Service → RabbitMQ → Payments Service → RabbitMQ → Orders Service

- Создание заказа  
- Отправка события `OrderCreated`  
- Обработка платежа  
- Обновление статуса заказа после получения события `PaymentProcessed`

### 2. Пополнение баланса и автоматическое выполнение ожидающих заказов
Клиент → API Gateway → Payments Service → RabbitMQ → Orders Service

- Пополнение счета  
- Генерация события `BalanceUpdated`  
- Orders Service автоматически проверяет и оплачивает ожидающие заказы  


## Асинхронная архитектура

### События и их роли
- `OrderCreatedEvent` — инициирует попытку оплаты при создании заказа  
- `PaymentProcessedEvent` — результат обработки платежа (успешен или нет)  
- `BalanceUpdatedEvent` — сигнал об изменении баланса и возможной оплате ожиданий  

### Transactional Outbox
- Заказы и связанные события сохраняются в одной транзакции  
- Фоновые воркеры читают события из Outbox-таблиц и отправляют в RabbitMQ  
- Гарантированная доставка событий без потерь даже при сбоях  


## Взаимодействие микросервисов

### Типы коммуникации
- **Синхронная** — HTTP-запросы через API Gateway (например, создание заказа или пополнение баланса)  
- **Асинхронная** — события через RabbitMQ между Orders и Payments  
- **Service Discovery** — Docker DNS для обращения сервисов друг к другу по имени контейнера  


## Контейнеризация

- Каждый компонент — отдельный контейнер  
- Настройка через `docker-compose.yml`  
- Возможность быстрого масштабирования и запуска на любой машине  
- Упрощённая разработка и деплой
